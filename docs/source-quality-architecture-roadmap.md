# 信源质量架构演进路线图

> 版本：v2（2026-08-18）
> 范围：信源发现、分层、采集、验证、复用、度量——**不包含「双管道 + 主动索取材料」**（该方向暂缓，单独成案）。
> 目标：把「信源质量」从「依赖 LLM 单次搜索的运气」升级为「可沉淀、可声明、可度量、可并行」的**领域通用**架构能力。
> 核心原则：**机制通用，知识领域化**——通用引擎 + 可插拔的领域配置（Domain Profile）。

---

## 0. 问题基线（为什么需要架构演进，而不是打补丁）

当前信息查找是单管道串行 ReAct 循环：

```
Agent2 在 3 轮 × 40 turn 里 边搜→边抓→边快照→边回读
```

由此产生五个**结构性缺陷**（补丁解决不了）：

| 缺陷 | 表现 | 对应架构方案 |
|---|---|---|
| **零沉淀** | 每次调研从零搜，验证过的权威源不积累 | 阶段 2 · 信源库 |
| **串行吞吐锁** | 发现/抓取/回读同走 LLM 步数，`max_turns` 锁死源数量 | 阶段 3 · 发现/抓取解耦 + 批量 worker |
| **标准后置** | 「每个问题要什么等级证据」采集完才知道 | 阶段 1 · 研究蓝图 |
| **不可度量** | 33 篇源好坏不可见，无反馈闭环 | 阶段 4 · 信源质量报告 |
| **知识层金融化** | S/A/B/D 定义、权威域名白名单、信源库内容都隐含「金融/股票」视角，换行业失效 | 阶段 0.5 · 领域配置层 |

> 前四个缺陷是「机制」问题，第五个是「知识」问题。机制层可通用，但**若不在架构里显式引入「领域配置层」，方案会退化成「腾讯/金融专用」**——这正是本路线图 v2 相对 v1 的核心补强。

---

## 1. 分期总览

```
阶段 0    ── 现状固化 + 度量基线（让质量可见）
阶段 0.5  ── 领域配置层 Domain Profile（让知识领域化，机制通用）
阶段 1    ── 研究蓝图（把等级要求前置到规划）
阶段 2    ── 信源库（把经验沉淀成资产）
阶段 3    ── 发现/抓取解耦 + 批量 worker（打破吞吐锁）
阶段 4    ── 信源质量报告 + 闭环（度量与自动改进）
```

**依赖关系**：
- 阶段 0 是所有人的度量地基（可与 0.5 并行）。
- **阶段 0.5 是所有「知识层」的地基**——阶段 1 的等级声明、阶段 2 的信源库、阶段 4 的质量报告都依赖「领域如何定义 S/A/B/D 与权威源」。
- 阶段 1 是阶段 2/3 的「标准来源」；阶段 2 为阶段 3 提供「从哪抓」；阶段 4 度量前五者的效果。

```
阶段0 ──→ 阶段0.5 ──→ 阶段1 ──→ 阶段2 ──→ 阶段3
   └──────────────────────→ 阶段4（横跨，度量前五者）
```

> 关键修正：**阶段 2（信源库）必须在阶段 0.5（领域配置）之后做**，否则信源库会按「公司/案例」组织、退化成腾讯专用，而不是按「领域」组织、跨公司复用。

## 2. 阶段 0：现状固化 + 度量基线（地基，低风险）

**目标**：在不改流程的前提下，先把「信源质量」变成可观测的指标，为后续每阶段提供「改造前 vs 改造后」的对比基线。

**交付物**：
1. **信源质量快照脚本**（CLI：`research-agent sources quality-report PROJECT`）
   - 输出 S/A/B/D 分布、每个必答问题的最高证据等级、一手源覆盖率、转述占比。
2. **指标定义**（写入文档，成为后续阶段的验收标准）：
   - `S级覆盖率` = 有 S 级证据的必答问题数 / 必答问题总数
   - `一手源占比` = S 级源数 / 总源数
   - `转述占比` = 标题/元数据含「转述/据/援引」的 A/B 级源数 / 总源数
   - `每问题独立源数` = 每个必答问题的去重独立源数量

**改动点**：新增只读分析脚本，不改任何采集逻辑。**零回归风险**。

**验收**：对腾讯项目跑一遍，得到 4 个基线数字，存档作为后续对比。

## 2.5 阶段 0.5：领域配置层 Domain Profile（机制通用、知识领域化）

**目标**：把「什么算一手权威源」从**硬编码的金融视角**升级为**按领域可插拔的配置**。这是所有「知识层」（阶段 1 的等级声明、阶段 2 的信源库、阶段 4 的质量报告）的地基。

**为什么必须有这一层**：现成的 S/A/B/D 定义、`_AUTHORITATIVE_WEB_SUFFIXES` 白名单、信源库的组织方式，全都隐含「金融/股票」视角。若直接进入阶段 2，信源库会按「腾讯/公司」组织，退化成腾讯专用。领域配置层把它纠正为「按领域组织、跨公司复用」。

### 2.5.1 设计：通用机制 + 领域插件

```
通用引擎（代码里写死，跨行业不变）
  ├─ S/A/B/D 的「抽象语义」（不是示例）
  ├─ 证据链、等级门禁、信源库、质量报告这些机制
  │
领域配置 Domain Profile（按行业提供，可插拔）
  ├─ 该领域 S/A/B/D 的「具体示例」
  ├─ 该领域的「权威源判定规则」（替代硬编码白名单）
  ├─ 该领域的「信源桶」（信源库的组织单位）
  └─ 该领域的「质量指标口径」（如"转述"在该领域指什么）
```

### 2.5.2 S/A/B/D 的「语义」通用，「示例」领域化

| 级别 | 通用语义（引擎写死） | 金融领域示例 | 医药领域示例 | 消费领域示例 |
|---|---|---|---|---|
| **S** | 一手权威原始数据（法定披露/官方统计/原始实验数据） | 财报、交易所公告、央行 | 临床试验注册、FDA/NMPA 批件、顶刊论文 | 财报、海关进出口、统计局 CPI |
| **A** | 头部专业机构的研究产出 | 券商深度研报、Wind/彭博一致预期 | 专业药企报告、临床试验解读 | 尼尔森/欧睿行业报告 |
| **B** | 专业媒体的时效性补充 | 36氪、财新、彭博路透 | 医药行业垂直媒体 | 零售/消费行业媒体 |
| **D** | UGC/低可信，默认剔除 | 知乎、雪球 | 患者论坛、知乎 | 小红书种草、知乎 |

### 2.5.3 权威源判定：从「硬编码后缀」升级为「规则引擎」

**现状（金融专用）**：
```python
_AUTHORITATIVE_WEB_SUFFIXES = ("gov.cn", "hkexnews.hk", "sse.com.cn", "szse.cn", "cninfo.com.cn")
```

**改造（领域可插拔）**：
```python
# Domain Profile 里声明该领域的权威源判定规则
authority_rules = {
  "finance_cn": [
    {"match": "domain_suffix", "value": ["hkexnews.hk", "sse.com.cn", "szse.cn", "cninfo.com.cn"]},
    {"match": "path_prefix",  "value": ["/zh-cn/investors", "/investors"], "note": "上市公司 IR 官网"},
  ],
  "pharma": [
    {"match": "domain_suffix", "value": ["clinicaltrials.gov", "fda.gov", "nmpa.gov.cn"]},
  ],
  "consumer": [
    {"match": "domain_suffix", "value": ["stats.gov.cn", "customs.gov.cn"]},
  ],
}
```

采集时按**当前调研命中的领域**加载对应规则，而不是永远用金融那 5 个后缀。

### 2.5.4 信源库的组织单位 = 领域桶（而非公司）

```
❌ 腾讯专用：信源库里有「腾讯该看这 20 个网站」
✅ 领域通用：信源库按「领域桶」组织，桶内存「规则 + 已验证实例」

  领域桶「中国互联网上市公司」：
    规则：财报→IR官网/HKEXnews；回购→HKEXnews；版号→NPPA
    实例：腾讯IR（已验证 S）、网易IR（已验证 S）、NPPA 版号页（已验证 S）
    → 做「腾讯」和「网易」共享此桶

  领域桶「创新药」：
    规则：临床→clinicaltrials.gov；批件→FDA/NMPA；数据→顶刊
    实例：...
    → 做「创新药公司」自动命中此桶
```

### 2.5.5 交付物

1. `DomainProfile` 数据模型 + 若干内置领域（`finance_cn` / `pharma` / `consumer` / `tech_semiconductor` 起手）。
2. `authority_rules` 判定引擎，替换 `_AUTHORITATIVE_WEB_SUFFIXES`。
3. 领域路由：Agent1 规划时识别调研领域 → 全流程加载对应 Profile。

### 2.5.6 验收

用四个领域各举一个「什么算 S 级源」的例子，验证「同一引擎 + 不同 Profile」能正确判级——证明机制通用、知识领域化。**若某领域无法表达，说明抽象层次错了，需回到 2.5.2 调整。**

## 3. 阶段 1：研究蓝图（标准前置）

**目标**：让「每个必答问题需要什么等级的数据」在 Agent1 规划阶段就确定，而不是采集完才知道。等级声明**依据阶段 0.5 的领域配置**（当前调研命中的领域决定「什么数据该是 S 级」）。

**现状**：`research_requirements.json` 已有 `min_source_tier`、`require_numeric` 字段，但 Agent1 从不被要求去填（腾讯项目全是 `null`）。

**改造**：
1. **Agent1 规划时强制声明**（改 `strategist.md` + `strategist.py`）：
   - 每个必答问题必须填 `min_source_tier`（如「q1 最新财务数据 → S」）。
   - 声明依据：**加载当前领域的 Domain Profile**，用该领域的 S 级示例判断「这个问题该不该要 S 级」。
   - 未声明等级的必答问题，Agent1 阶段不通过（确定性校验，不是 prompt 软约束）。
2. **采集门禁升级**（改 `sources/quality.py` + `orchestrator.py`）：
   - 现有门禁只查「每个必答问题 ≥1 条证据」，升级为「必须达到 `min_source_tier` 声明的等级」。
   - 达不到 → 阻断，理由可见（不是静默降级）。
3. **抓不到显性化**（改 `collector_round.md` + 采集输出校验）：
   - 规划的 S 级源在采集后「要么入库、要么在 round_N.md 写明未获取原因」。
   - 缺失判定「S 级覆盖不达标」，触发补采或提示。

**改动点**：`research_plan.py`（校验）、`strategist.md`（声明要求 + 领域配置注入）、`quality.py`（等级门禁）、`collector_round.md`（显性化）。

**验收**：新建一次调研，`research_requirements.json` 每个必答问题都有 `min_source_tier`（且符合当前领域的 S 级语义）；门禁能因「等级不足」阻断。

## 4. 阶段 2：信源库（经验沉淀成资产）★ 最根本

**目标**：建立**跨项目持久化的权威信源目录**，Agent2 从信源库出发采集，WebSearch 只做增量。

**现状**：`SourceAsset` 有 `collection_id` 字段，但「collection」概念基本没用起来；信源按 `project_id` 隔离，无法跨项目复用。

**设计**：
1. **信源库（Source Registry）数据模型**（新增，与项目信源分离，**按领域桶组织**）：
   ```
   RegistryEntry:
     entry_id, domain_profile (领域桶，如 finance_cn / pharma),
     canonical_url, url_template, domain,
     publisher, source_tier (S/A/B/D), tier_rationale,
     capture_method (web_fetch / upload / api),
     availability_status (known_good / flaky / login_required / paywalled),
     last_verified_at, verification_evidence_count,
     topics/tags, usage_count, trust_score
   ```
2. **「验证过的源」自动入库**：Agent3 每次 `RecordProjectEvidence` 成功（尤其 S 级），把该源登记进**其所属领域桶**，更新 `trust_score` 和 `usage_count`。
3. **Agent2 采集时优先查信源库**：新增 `SearchSourceRegistry` 工具，按「当前领域 + 等级」返回该领域桶内的已知权威源，Agent2 先采这些，再用 WebSearch 补增量。
4. **可用性状态**：抓失败的源标记 `paywalled/login_required/flaky`，下次直接跳过或提示人工，避免反复撞墙。
5. **领域桶共享**：同一领域桶内的源跨公司复用（腾讯、网易共享「中国互联网上市公司」桶），这是信源库通用性的关键。

**改动点**：新增 `sources/registry.py` + 数据库表、`RegistryEntry` 模型（含 `domain_profile` 字段）、`SearchSourceRegistry` 工具、采集 prompt 注入信源库命中。

**验收**：跨两次同类调研，第二次能复用第一次验证过的 S 级源；**跨两个同领域公司**（如腾讯→网易）也能复用同一领域桶的源；抓不到的源有可用性标记，不再静默跳过。

**关键设计原则**：
1. 信源库是「线索与分级经验」，不是「证据副本」——证据仍必须在项目内快照留证，信源库只是告诉 Agent「该去哪抓、等级该是什么」。
2. **信源库的组织单位是「领域桶」而非「公司」**——这依赖阶段 0.5 的领域配置，是通用性的根基。

## 5. 阶段 3：发现/抓取解耦 + 批量 worker（打破吞吐锁）

**目标**：把「LLM 的发现」和「确定性的抓取」分层，吞吐不再被 `max_turns` 锁死。

**现状**：LLM 串行地 搜→抓→快照→回读，每个源消耗多步 LLM turn。

**改造**：
1. **发现阶段（轻量）**：LLM 一轮吐出「候选源清单」：URL + 判级 + 依据（不再逐个抓）。
2. **抓取阶段（确定性批量）**：worker 并行抓取 + 快照 + 解析，不受 LLM 步数限制。
3. **失败回灌**：抓取结果（成功/失败/降级）批量回传，LLM 只处理失败清单和降级决策。

**改动点**：新增抓取 worker（可复用现有 `sources/jobs.py` 的 job 队列）、把 `CaptureProjectWebSource` 拆成「批量注册」接口、采集 prompt 改为「先列清单，再批量抓」。

**验收**：一次采集能快照的源数量不再受 `max_turns` 线性约束；抓 100 个候选源的时间与抓 10 个不在同一数量级。

**前置**：依赖阶段 2 的信源库（「从哪抓」），否则批量抓的候选质量不可控。

---

## 6. 阶段 4：信源质量报告 + 闭环（度量与自动改进）

**目标**：交付物带「信源质量报告」，让质量可见、可追溯、可自动改进。指标口径**按阶段 0.5 的领域配置**解释（如「转述」在金融领域指「媒体转述券商」，在医药领域指「媒体转述临床数据」）。

**改造**：
1. **交付物附带质量报告**：每次调研交付时生成 `06_source_quality.md`，含阶段 0 定义的指标 + S/A/B/D 明细 + 每问题最高等级 + 该领域的 S 级示例对照。
2. **质量信号回灌信源库**：报告中的「一手源覆盖率低」「某源反复抓失败」等信号，自动更新**对应领域桶**的 `trust_score` / `availability_status`。
3. **首页/成果中心可视化**：信源质量报告在 Web 工作台可见（成果中心新增「信源质量」页签）。

**改动点**：新增质量报告生成器（复用阶段 0 的脚本逻辑 + 阶段 0.5 的领域语义）、报告接入交付流水线、Web 展示。

**验收**：每次调研交付都能看到信源质量报告；报告能按当前领域正确解释指标；信源库对应领域桶的信任分随实际使用动态更新。

## 7. 与现有架构的关系（不破坏既有设计）

| 现有设计 | 演进后 | 保持不变 |
|---|---|---|
| `sources/quality.py` 确定性质量门 | 升级为「等级门禁」 | 核心逻辑不变，只加等级判断 |
| `_AUTHORITATIVE_WEB_SUFFIXES` 硬编码白名单 | 领域配置的 `authority_rules` | 判定逻辑不变，规则来源改为领域 Profile |
| `SourceAsset.collection_id` | 信源库的 `RegistryEntry`（含 domain_profile） | 项目信源仍按 project 隔离 |
| `CaptureProjectWebSource` | 拆成「批量注册」 | 单源快照语义不变 |
| `research_requirements.min_source_tier` | 从「可选」变「必填」+ 领域语义 | schema 不变，只加强校验 |
| ReAct 采集循环 | 发现/抓取解耦 | 验证（Agent3）仍走 ReAct |

**核心约束**：
1. 信源库只存「线索与分级经验」，**证据仍必须在项目内快照留证**——绝不削弱现有的「确定性证据链」防线。
2. **领域配置层只提供「知识」，不替代「机制」**——S/A/B/D 的抽象语义和门禁逻辑写死在引擎里，领域 Profile 只提供「示例、判定规则、桶内容」。

## 8. 风险与回退

| 阶段 | 主要风险 | 回退策略 |
|---|---|---|
| 0 | 几乎无 | 只读脚本，可随时删 |
| 0.5 | 领域抽象层次错误（某领域无法表达） | 回到 2.5.2 调整抽象语义；内置领域可先只保留 finance_cn 兜底 |
| 1 | 等级门禁过严，卡住调研 | `min_source_tier` 留空回退到现状（等级门禁只对已声明的生效） |
| 2 | 信源库污染（低质源被标 S） | 入库需 Agent3 验证成功 + 人工可修正分级 |
| 3 | 批量抓取失控（抓太多垃圾） | 依赖阶段 2 的候选清单做前置过滤 |
| 4 | 指标误导 | 指标只做观测，不做自动阻断（阻断仍由阶段 1 门禁决定） |

## 9. 建议的推进节奏

1. **立即做阶段 0**（1 天工作量）：产出腾讯项目的信源质量基线，锁定「改造前」数字。
2. **阶段 0.5**（2-3 天）：领域配置层——先做 `finance_cn` 一个领域（覆盖现有腾讯/金融场景），再补 `pharma`/`consumer`/`tech_semiconductor` 验证通用性。
3. **阶段 1**（2-3 天）：等级声明 + 等级门禁，立刻让「必须一手数据」变成硬约束（依赖 0.5 的领域语义）。
4. **阶段 2**（1-2 周）：信源库，这是架构质变，但也是最大的新增（依赖 0.5 的领域桶组织）。
5. **阶段 3**（1-2 周）：依赖阶段 2，吞吐优化。
6. **阶段 4**（持续）：度量闭环，与阶段 2/3 并行。

> **阶段 0 和 0.5 可以并行启动**（0 是度量基线、0.5 是领域配置，互不依赖）；阶段 1 依赖 0.5；阶段 2 是中期核心且强依赖 0.5；阶段 3 依赖阶段 2。
> 修正说明（v2）：阶段 2 不能跳过阶段 0.5 直接做，否则信源库会退化成「腾讯/金融专用」。

## 附录 A：通用性自检清单（每个阶段做完对照）

在实现每个阶段时，用以下问题自检「是否仍然领域通用」：

1. 这段代码里有没有**硬编码某个行业/公司的专有名词**（券商、财新、腾讯、A股）？
2. 这段逻辑换成**医药/消费/科技**领域，是否还能工作？
3. 这个数据模型的组织单位是**「领域」**还是**「公司/案例」**？
4. 这个判定规则是**「领域可插拔」**还是**「写死在引擎里」**？
5. 这个指标口径，在非金融领域是否还有意义？

若任一题答「否」，说明该阶段实现退化了，需回到阶段 0.5 的抽象层次修正。
